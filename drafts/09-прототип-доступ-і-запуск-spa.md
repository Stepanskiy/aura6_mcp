# 9. Прототип: аутентифікація, доступ по фірмах і запуск SPA з чату

Частина опису прототипу (див. [06-прототип.md](варіант-облік-з-осв/06-прототип.md)). Облікова частина — довідники, проводки, SPA операцій — у [10-прототип-облік-і-spa.md](варіант-облік-з-осв/10-прототип-облік-і-spa.md).

## Принцип: модель — навігатор

Модель знає, які SPA є і коли яку відкрити, але не бачить жодного облікового рядка: ні в результатах tools, ні в `_meta`, ні через resources. Дані ходять тільки між браузером користувача і сервером Аури. Це третій рівень ізоляції з [04-чутливі-дані-і-ризики.md](04-чутливі-дані-і-ризики.md), застосований до всього прототипу, а не лише до зарплати.

Це гарантується структурою коду, а не дисципліною: MCP-адаптер — окремий модуль, який не залежить від модулів читання даних. Tool фізично не може повернути проводку чи залишок.

```
Користувач ── чат (Claude / ChatGPT) ── MCP + OAuth ──► Аура: MCP-адаптер (тільки open_* tools)
                    │                                        │ тікет у _meta
                    │ iframe ui://aura/<spa>                 │
                    ▼                                        ▼
                   SPA ── fetch напряму (тікет → сесія) ──► Аура: API ──► PostgreSQL (RLS)

Keycloak (OIDC) — засвідчує, хто користувач, для обох каналів
```

## Аутентифікація

Keycloak, realm `aura`. Аура зберігає лише `sub` користувача, а всі права тримає у своїй БД (див. «Доступ по фірмах»).

| Клієнт Keycloak | Тип | Для чого |
|---|---|---|
| Claude, ChatGPT | Dynamic Client Registration | OAuth MCP-коннектора |
| `aura-spa` | public, PKCE | SPA поза чатом (`apps.<домен>`) |
| `aura` | resource server | Сервер Аури перевіряє токени через JWKS |

У Keycloak є лише одна realm-роль — `aura_admin`. Права по фірмах змінюються часто і мають бути доступні RLS у PostgreSQL, тому вони живуть в Аурі, а Keycloak лише засвідчує, хто прийшов.

Під час першого входу користувач створюється в Аурі автоматично, але без доступу до жодної фірми. Доступ надає адміністратор.

### Запуск SPA з чату

1. Користувач пише: «рознеси виписку за жовтень». Модель викликає `open_bank_statement({ period: "2026-10" })`.
2. MCP-адаптер перевіряє токен і те, що SPA доступна користувачу (є хоча б одна фірма з потрібною роллю). Якщо ні — коротка відмова без подробиць.
3. Адаптер створює тікет: 256 біт випадковості, живе 60 секунд, використовується один раз. Тікет привʼязаний до `sub`, конкретної SPA і параметрів запуску.
4. Відповідь tool: моделі — текст «Відкрито SPA “Банківська виписка”», хосту — ui-ресурс SPA, тікет — у `_meta` (моделі не показується).
5. SPA обмінює тікет на сесію: `POST /api/auth/ticket` → JWT на 30 хвилин з правами лише цієї SPA. Токен зберігається в памʼяті iframe, без cookies, бо сторонні cookies в iframe блокуються.
6. Далі SPA звертається до API Аури напряму. Домен дозволений у `_meta.ui.csp.connectDomains`.

Коли сесія закінчується, SPA пропонує відкрити її з чату ще раз. Довгоживучих refresh-токенів в iframe немає.

Якщо тікет і потрапить у контекст моделі чи в логи, він уже використаний або протухне за хвилину.

### SPA поза чатом

Ця ж збірка SPA розміщується на `apps.<домен>` із входом через Keycloak (PKCE) і працює з тим самим API та тими самими правами. Це потрібно для налагодження, а також як запасний шлях, якщо в якомусь клієнті не працюють MCP Apps.

## MCP: інструменти запуску SPA

| Tool | Коли модель його викликає | Параметри |
|---|---|---|
| `open_bank_statement` | Завантажити, рознести або переглянути банківську виписку | `period?`, `firm_hint?` |
| `open_income_expense` | Внести дохід чи витрату: рахунок або акт постачальника, акт покупцю, нарахування | `kind?: income \| expense`, `firm_hint?` |
| `open_trial_balance` | ОСВ, сальдо, обороти, залишки, заборгованість | `period?`, `firm_hint?` |
| `open_postings_journal` | Переглянути проводки | `period?`, `firm_hint?` |
| `open_admin` | Довідники, доступи користувачів до фірм (тільки `aura_admin`) | `section?` |

Параметри задають лише контекст запуску, а не дані. `firm_hint` — текст, як його сказав користувач («Альфа»). SPA шукає збіг тільки серед доступних користувачу фірм; якщо не знаходить, показує звичайний вибір. Модель про результат пошуку не дізнається.

Набір tools залежить від прав. Хто не має ролі `operator` у жодній фірмі, не бачить `open_bank_statement` і `open_income_expense`.

Точність вибору SPA (гіпотеза 1) залежить насамперед від описів tools. Кожен опис містить типові фрази користувачів і межі застосування, наприклад: «Не для перегляду залишків — для цього open_trial_balance».

## Доступ по фірмах

Фірма — балансова одиниця. Права користувача задаються окремо для кожної фірми.

### Ролі

| Роль | Рівень | Може |
|---|---|---|
| `viewer` | фірма | Журнал проводок, ОСВ |
| `operator` | фірма | Те саме, що `viewer`, плюс банківські виписки, доходи/витрати, створення контрагентів |
| `accountant` | фірма | Те саме, що `operator`, плюс ручні операції, грошові рахунки фірми, закриття періоду |
| `aura_admin` | глобально | Фірми, валюти, статті обліку; надання доступів до фірм |

Ролі накопичуються знизу вгору. В одній фірмі користувач може бути `accountant`, в іншій — `viewer`, до третьої взагалі не мати доступу.

### Що кому видно

| Дані | Видимість |
|---|---|
| Фірми | Тільки ті, до яких є доступ |
| Грошові рахунки, операції, проводки | Тільки доступних фірм |
| Валюти, статті обліку | Усім автентифікованим |
| Контрагенти | Усім автентифікованим (спільний довідник холдингу); чи обмежувати — відкрите питання |

Без фільтра по фірмі ОСВ і журнал показують усі доступні фірми з розбивкою по кожній. Запит із явно вказаною недоступною фірмою отримує помилку `firm_access_denied`, а не порожній результат.

### Дві лінії захисту

1. **Код.** Кожна команда і кожен запит проходять політику (користувач, фірма, дія) ще до звернення до БД.
2. **PostgreSQL RLS.** Сервер підключається до БД роллю без `BYPASSRLS`. Кожен запит виконується в транзакції з `SET LOCAL aura.user_id`. Політики на таблицях з `firm_id`: читання — будь-яка роль у фірмі; запис — роль, достатня для дії (функція `aura.has_firm_role(firm_id, role)`).

Перевірка гіпотези 3: тести доступу проганяються ще раз із вимкненою першою лінією. Результат має бути тим самим.
