# 6. Прототип (PoC)

## Принцип: Аура 3 — орієнтир, а не специфікація

Рішення з 1С напряму не копіюються. Документація Аури 3 і звіт по конфігурації потрібні, щоб мати уяву про необхідний функціонал: які процеси є в холдингу, які сутності й правила вони зачіпають, що не можна загубити.

Модель даних, процеси й алгоритми Аури 6 проєктуються заново під нову концепцію. Аура 3 використовується так:

- **як чек-лист функціоналу** — щоб нічого суттєвого не пропустити;
- **як джерело тестових даних** — реальні фірми, контрагенти, статті, виписки для перевірки сценаріїв;
- **для звірки результатів** — коли нова система рахує те саме (наприклад, ОСВ чи заборгованість), цифри можна порівняти з Аурою 3.

## Зріз прототипу

Прототип перевіряє не окрему предметну область, а фундамент, на якому стоятимуть усі модулі: облік у проводках, доступ по фірмах і роботу через SPA, які запускаються з чату, без передачі даних моделі.

| Що є на сервері | Зміст | Детально |
|---|---|---|
| Аутентифікація | Keycloak (OIDC); сервер Аури — resource server | [09](../09-прототип-доступ-і-запуск-spa.md) |
| Контроль доступу | Права користувача окремо по кожній фірмі; перевірка в коді і RLS | [09](../09-прототип-доступ-і-запуск-spa.md) |
| Базові довідники | Фірми, Валюти, Контрагенти, Статті обліку, Грошові рахунки | [10](10-прототип-облік-і-spa.md) |
| Проводки | Базове читання (журнал, ОСВ по фірмах) і запис | [10](10-прототип-облік-і-spa.md) |
| Механізм операцій | Тип операції = схема + правило формування проводок. SPA подає операцію, проводки формує сервер | [10](10-прототип-облік-і-spa.md) |
| SPA | Банківська виписка, Доходи/витрати, ОСВ, Журнал проводок | [10](10-прототип-облік-і-spa.md) |
| MCP | Лише інструменти запуску SPA. Модель знає, яку SPA відкрити, але до даних доступу не має | [09](../09-прототип-доступ-і-запуск-spa.md) |

Фірма — балансова одиниця: оборотно-сальдова відомість ведеться і закривається окремо по кожній фірмі.

**Поза зрізом:** проєкти, Ф2/Ф3/Ф4, підписи, зарплата, бюджети, курсові різниці, внутрішньогрупові операції, Code Mode, користувацькі SPA. Попередній варіант зрізу (проєкти → роботи → Ф2/Ф3 → підписи → платежі) переноситься на наступний етап і спиратиметься на цей фундамент.

## Гіпотези

| # | Гіпотеза | Експеримент | Критерій успіху |
|---|---|---|---|
| 1 | Модель — достатній навігатор | 20–30 фраз користувачів («рознеси виписку Привату за жовтень», «треба внести рахунок за оренду», «покажи сальдо по Альфі») у Claude і ChatGPT | ≥ 90% фраз відкривають потрібну SPA з правильними параметрами |
| 2 | Дані не проходять через модель | SPA в iframe працює з API Аури напряму (`connectDomains` + одноразовий тікет). Перевіряються транскрипт, логи MCP-адаптера і трафік | У контексті моделі і в трафіку MCP немає жодних облікових даних — в обох клієнтах |
| 3 | Доступ по фірмах контролюється сервером | Три користувачі з різними наборами фірм; прямі запити до API з чужою фірмою; тести з вимкненою перевіркою в коді | Видно і доступно тільки дозволене; RLS блокує навіть при помилці в коді |
| 4 | Проводки формує тільки сервер | SPA подає операції; спроби з неповною аналітикою, у закритий період, повтор з тим самим ключем, повторний імпорт виписки | Некоректне відхилено зі структурованою помилкою; повтори не дублюють проводки |
| 5 | ОСВ сходиться | Виписки і доходи/витрати на синтетичних, потім реальних даних | По кожній фірмі Дт-обороти = Кт-обороти; залишок рахунку = залишок у виписці; цифри збігаються з ОСВ Аури 3 |
| 6 | Новий тип операції додається без змін ядра | Додати третій тип операції (наприклад, переміщення коштів між власними рахунками) | Потрібні лише нова схема, правило і SPA; ядро, доступ і ОСВ не змінюються |

Гіпотезу 2 перевіряти першою: якщо прямий `fetch` з iframe не працює в одному з клієнтів, змінюється схема роботи всіх SPA.

## Що потрібно

Поточний стан підготовки — у чек-листі [08-підготовка-до-прототипу.md](../08-підготовка-до-прототипу.md).

### Акаунти й доступи

- **Claude**: план із підтримкою власних коннекторів (remote MCP) та MCP Apps. Для командного тесту — Team або Enterprise; почати самому можна на Pro/Max. Назви планів і їх можливості перевірити в поточному прайсі.
- **ChatGPT**: Plus/Pro або Business з увімкненим Developer Mode для MCP-коннекторів; Apps SDK для віджетів.
- **Тестові користувачі**: мінімум три облікові записи в обох клієнтах з різним доступом. Наприклад: оператор однієї фірми; бухгалтер двох фірм; переглядач усіх фірм плюс `aura_admin`.
- **IdP**: Keycloak у Docker (безкоштовно, див. [03-стек-технологій.md](../03-стек-технологій.md)).

### Інфраструктура

- Публічний HTTPS-ендпоінт: remote MCP викликають сервери Anthropic/OpenAI, а не браузер. Стенд — VPS (див. [../deploy/](../deploy/)). Домен потрібен справжній: на нього дивляться CSP і OAuth-редиректи.
- PostgreSQL 16+ у Docker.
- Піддомен `apps.<домен>` для SPA поза чатом.
- Машина розробника: Node 22, pnpm, Docker.

### Дані

- **Вивантаження з 1С** по 2–3 фірмах (організаціях) за рік:
  - довідники: організації, валюти, контрагенти (з ЄДРПОУ та IBAN), статті обліку, банківські рахунки й каси;
  - вхідні залишки по грошових рахунках і розрахунках на початок року;
  - банківські виписки у файлах, як їх отримують з банку, за 2–3 місяці;
  - ОСВ Аури 3 за ті самі місяці — для звірки.
- **Синтетика до вивантаження:** 3 фірми, 2 валюти, ~50 контрагентів, план статей, 5–6 грошових рахунків, виписки на 3 місяці.
- **BSL-модулі не потрібні**: логіка Аури 6 проєктується заново, а не переноситься з 1С.
- **Набір сценаріїв**:
  - 20–30 фраз, як їх реально скажуть оператор, бухгалтер і фіндиректор, з очікуваною SPA і параметрами;
  - 10–15 облікових сценаріїв з очікуваними проводками.

  Без цього PoC не вимірюється.

### Люди і час

- Один розробник TypeScript на повний день, бажано з досвідом PostgreSQL. Досвід MCP не обовʼязковий.
- Носій домену (бухгалтер або фіндиректор): план статей, правила рознесення виписки, сценарії, оцінка результатів. Приблизно 2–3 години на тиждень.

## План на 4 тижні

| Тиждень | Що робимо |
|---|---|
| 1 | Модель даних, довідники і синтетичні дані; OIDC у Keycloak; доступ по фірмах і RLS; API проводок (`manual`, журнал, ОСВ) |
| 2 | Механізм типів операцій; тип і SPA «Доходи/витрати»; MCP-адаптер з `open_*` і обміном тікета; перевірка гіпотези 2 у Claude і ChatGPT |
| 3 | Тип і SPA «Банківська виписка» (розбір, підказки, звірка залишку); SPA ОСВ і журналу; SPA поза чатом |
| 4 | Третій тип операції (гіпотеза 6); імпорт реальних даних і звірка з Аурою 3; прогін сценаріїв; звіт за таблицею гіпотез |

## Що можна зробити одразу, без вивантаження з 1С

1. **Модель даних** за [10-прототип-облік-і-spa.md](10-прототип-облік-і-spa.md). Звіт по конфігурації використовується як перелік реквізитів довідників і для мапінгу при імпорті з 1С.
2. **Каркас монорепо**:
   - `core` — Zod-контракти, доступ, типи операцій і правила проводок;
   - `api` — REST + OpenAPI;
   - `mcp` — тільки запуск SPA, без залежності від модулів читання даних;
   - `apps/bank-statement`, `apps/income-expense`, `apps/trial-balance`, `apps/postings-journal`.
3. **Генератор синтетичних даних** на базі схеми. Потім синтетика замінюється реальними даними без зміни коду.
4. **Таблиці правил проводок** для обох типів операцій: «payload → очікувані проводки». Їх перевіряє носій домену ще до появи коду.

## Після PoC

1. **Тіньовий режим.** Проводки з 1С переносяться в PostgreSQL, ОСВ Аури 6 звіряється з Аурою 3, поки 1С лишається основною системою.
2. **Нові модулі на фундаменті прототипу.** Проєкти, Ф2/Ф3, платежі, бюджети — нові типи операцій і нові SPA. Окремо вирішується, де модель має право бачити дані, а де лишається навігатором.
3. **Запис по модулях.** Модулі по черзі переходять на нову систему, 1С по кожному модулю вимикається окремо.
