# 10. Прототип: довідники, проводки і SPA операцій

Частина опису прототипу (див. [06-прототип.md](06-прототип.md)). Аутентифікація, доступ по фірмах і запуск SPA з чату — у [09-прототип-доступ-і-запуск-spa.md](../09-прототип-доступ-і-запуск-spa.md).

## Модель обліку

Облік ведеться в проводках, окремо по кожній фірмі. Окремого плану рахунків у прототипі немає: його роль виконують статті обліку, а аналітику дають контрагенти і грошові рахунки.

Проводка — це пара Дт і Кт з однією сумою. Баланс забезпечується самою структурою даних, тож окрема перевірка «Дт = Кт» не потрібна. Складні господарські операції складаються з кількох проводок.

В Аурі 3 облік ведеться за планом рахунків з субконто, а статті обліку — окремий довідник із привʼязкою до рахунків. В Аурі 6 це спрощено до одного рівня (див. [06-прототип.md](06-прототип.md), принцип «Аура 3 — орієнтир»).

## Довідники

### Фірми

Код, назва, ЄДРПОУ, базова валюта, `closed_until` — дата, до якої включно період закрито.

### Валюти

Код ISO 4217, назва, кількість знаків після коми.

### Контрагенти

Назва, ЄДРПОУ або ІПН, список IBAN (за ними виписка знаходить контрагента), ознака «заблокований».

### Статті обліку

| Реквізит | Значення |
|---|---|
| Код, назва | |
| Група | Ієрархія; групу не можна використати в проводці |
| Вид | `money` — грошові кошти; `settlement` — розрахунки; `income` — доходи; `expense` — витрати; `equity` — капітал; `other` |
| Обовʼязкова аналітика | Випливає з виду: `money` → грошовий рахунок; `settlement` → контрагент; `income`/`expense` → контрагент необовʼязковий; решта → без аналітики |
| Системний код | Для статей, на які посилаються правила проводок: `MONEY`, `AR` (розрахунки з покупцями), `AP` (розрахунки з постачальниками), `TRANSIT` (переміщення коштів), `OPENING` (введення залишків). Правила посилаються на код, а не на id |
| Заблокована | Нові проводки заборонені |

Початковий перелік статей береться з довідника СтатьиУчета Аури 3: його реквізити Доход, Затрата, Баланс, ФР, ДДС підказують вид статті. Набір видів при цьому новий.

### Грошові рахунки

Фірма, тип (`bank` або `cash`), назва, IBAN і банк, валюта, ознака «є виписка», ознака «активний».

## Проводки

| Поле | Зміст |
|---|---|
| `operation_id`, `version` | Операція і версія операції, яка сформувала проводку |
| `firm_id` | Фірма |
| `date` | Дата обліку |
| `currency`, `amount` | Валюта і сума: `numeric(18,2)`, більше нуля |
| `dt_article`, `dt_counterparty`, `dt_cash_account` | Сторона Дт: стаття і аналітика |
| `kt_article`, `kt_counterparty`, `kt_cash_account` | Сторона Кт |
| `memo` | Зміст |

### Інваріанти

Перевіряються сервером для будь-якої операції; ключові з них продубльовано обмеженнями БД.

- Обидві сторони — незаблоковані статті, які не є групами.
- Аналітика відповідає виду статті: обовʼязкова заповнена, зайва порожня.
- Грошовий рахунок належить фірмі проводки, і валюта проводки збігається з валютою рахунку.
- Дата пізніша за `closed_until` фірми.
- Проводки незмінні. Права БД дозволяють лише вставку, а `UPDATE` і `DELETE` заборонені.

### Версії операцій

Зміна чи скасування операції створює нову версію з новим набором проводок; скасування — це версія без проводок. ОСВ і журнал читають тільки поточні версії. Історія зберігається автоматично, і можна відновити, яким був стан на будь-яку дату.

Операцію не можна змінити, якщо стара або нова дата потрапляє в закритий період.

## Операції: як різні SPA формують різні проводки

SPA ніколи не надсилає проводки. Вона надсилає операцію свого типу, а проводки з неї формує сервер за правилом цього типу.

```
SPA ── POST /api/operations/{type}  { payload, idempotency_key } ──► сервер:
          1. схема типу (Zod): структура і обовʼязкові поля
          2. доступ: роль у фірмі, достатня для цього типу
          3. правило типу: payload + довідники → проводки
          4. загальні інваріанти проводок (див. вище)
          5. одна транзакція: операція + версія + проводки + аудит
    ◄── { operation_id, version, postings }  або  { code, path, message }
```

### Тип операції

Кожен тип реєструється в ядрі і складається з таких частин:

| Складова | Що це |
|---|---|
| `type` | `bank_statement`, `income_expense`, `manual` |
| Схема | Zod-схема payload; з неї генеруються JSON Schema і TS-типи для SPA |
| Мінімальна роль | `operator` або `accountant` |
| Правило проводок | Чиста функція `(payload, довідники) → проводки[]` |
| Додаткові перевірки | Специфічні для типу, наприклад звірка залишку виписки |

Що з цього випливає:

- Інваріанти проводок перевіряються в одному місці — незалежно від типу операції і від SPA.
- Правило — чиста функція, тож тестується таблицею «payload → очікувані проводки» без БД.
- Новий тип операції — це схема, правило і SPA. Ядро, доступ і ОСВ при цьому не змінюються (гіпотеза 6).
- Відповідь містить сформовані проводки, і SPA показує, що саме записано. Це результат запису, а не превʼю перед ним.

### Помилки

Помилка вказує на поле, яке треба виправити, і SPA підсвічує його:

```json
{ "code": "analytics_required",
  "path": "lines[3].counterparty",
  "message": "Стаття 3610 «Розрахунки з постачальниками» вимагає контрагента" }
```

### Ідемпотентність

`idempotency_key` унікальний у межах користувача: повторний виклик повертає той самий результат і нічого не записує вдруге. Крім того, у типів є природні ключі. Наприклад, ID банківської транзакції не дає провести той самий рядок виписки двічі.

### `manual` — базовий запис проводок

Payload — це безпосередньо список проводок. Потрібна роль `accountant`. Тип використовується для виправлень і введення початкових залишків (через статтю `OPENING`).

## Читання

- **Журнал проводок.** Фільтри: фірми, період, стаття, контрагент, грошовий рахунок, тип операції. Пагінація.
- **ОСВ.** Параметри: фірми (за замовчуванням усі доступні), період, групування (стаття, далі контрагент або грошовий рахунок), валюта. Колонки: сальдо на початок Дт/Кт, обороти Дт/Кт, сальдо на кінець Дт/Кт.
  - ОСВ завжди розбита по фірмах: фірма — балансова одиниця, згортання між фірмами немає.
  - По кожній фірмі підсумок Дт дорівнює підсумку Кт.
- **Залишок грошового рахунку на дату** — для звірки виписки.

Мультивалютність у прототипі: ОСВ групується по валюті, перерахунку в базову валюту немає (див. відкриті питання в [07-рішення-і-відкриті-питання.md](../07-рішення-і-відкриті-питання.md)).

ОСВ рахується безпосередньо з проводок за індексом (фірма, дата, стаття). Таблиці підсумків з'являться, коли цього вимагатимуть обсяги.

## SPA «Банківська виписка»

### Сценарій

1. Користувач вибирає фірму і грошовий рахунок. Доступні лише фірми користувача і рахунки типу `bank` з ознакою «є виписка».
2. Користувач завантажує файл. Розбір виконує сервер (`POST /api/bank-statements/parse`), нічого не записуючи. Формати для прототипу: CSV ПриватБанку і monobank, формат обміну з клієнт-банком (`1CClientBankExchange`). Які банки використовуються фактично, ще треба уточнити.
3. Сервер повертає рядки з підказками:
   - контрагент — за ЄДРПОУ або IBAN;
   - стаття — за останнім рознесенням цього контрагента в тому самому напрямку;
   - статус «вже проведено» — за ID банківської транзакції.
4. Користувач дозаповнює рядки: створює нового контрагента просто з рядка, вибирає статтю там, де сервер не дав підказки.
5. `POST /api/operations/bank_statement` — одна операція на виписку.

### Перевірки сервера

- У кожного рядка є стаття і аналітика, якої вона вимагає.
- Рядок з тим самим ID транзакції на цьому рахунку вже проведено — рядок відхиляється (унікальний ключ: грошовий рахунок + ID транзакції).
- Вхідний залишок виписки дорівнює залишку рахунку в Аурі на початок періоду. Якщо ні — відмова `opening_balance_mismatch` з обома сумами. Перший залишок вводиться операцією `manual` зі статтею `OPENING`.
- Дати рядків лежать у межах періоду виписки і не потрапляють у закритий період.
- Валюта виписки дорівнює валюті рахунку.

### Проводки по рядку

| Рядок | Дт | Кт |
|---|---|---|
| Надходження | `MONEY` · грошовий рахунок | Стаття рядка · її аналітика |
| Списання | Стаття рядка · її аналітика | `MONEY` · грошовий рахунок |

Типові статті рядка:

| Стаття | Коли |
|---|---|
| `AR` | Оплата від покупця |
| `AP` | Оплата постачальнику |
| Стаття витрат | Комісія банку |
| Стаття доходів | Відсотки на залишок |
| `TRANSIT` | Переказ між власними рахунками. Обидві виписки проводяться через `TRANSIT`, і після обох його сальдо дорівнює нулю — це видно в ОСВ |

## SPA «Доходи / витрати»

Для нарахувань: рахунки й акти постачальників, акти покупцям, інші доходи й витрати.

- **Шапка:** фірма, дата, вид (дохід або витрата), контрагент, валюта.
- **Рядки:** стаття (для доходу — тільки статті виду `income`, для витрати — тільки `expense`), сума, коментар.

| Вид | Дт | Кт |
|---|---|---|
| Витрата | Стаття витрат · контрагент | `AP` · контрагент |
| Дохід | `AR` · контрагент | Стаття доходу · контрагент |

Оплата тут не вводиться: вона приходить з банківської виписки (Дт `AP`, Кт `MONEY`), інакше гроші врахувались би двічі.

Виняток — грошові рахунки без виписки, наприклад каса. Для них SPA дозволяє позначку «оплачено одразу» і додає проводку оплати. Якщо позначити «оплачено одразу» для рахунку, по якому є виписка, сервер поверне помилку `payment_must_come_from_statement`.

Сальдо `AP` і `AR` по контрагенту в ОСВ і є заборгованістю: нарахування з цієї SPA мінус оплати з виписки.

## SPA «ОСВ» і «Журнал проводок»

Тільки читання. З рядка ОСВ можна перейти в журнал з тими самими фільтрами, а з проводки — в операцію і в SPA, яка її створила.

## API прототипу

Одне API для SPA в чаті і поза ним. MCP-адаптер його не викликає.

| Метод | Що робить |
|---|---|
| `GET /api/me` | Користувач, його фірми і ролі |
| `GET /api/firms`, `/currencies`, `/counterparties`, `/articles`, `/cash-accounts` | Довідники з урахуванням доступу |
| `POST`/`PATCH` на довідники | Запис довідників відповідно до ролі |
| `POST /api/operations/{type}` | Запис операції, ідемпотентний |
| `GET /api/operations/{id}` | Операція з версіями і проводками |
| `POST /api/bank-statements/parse` | Розбір файлу виписки без запису |
| `GET /api/postings` | Журнал проводок |
| `GET /api/reports/trial-balance` | ОСВ |
| `GET /api/cash-accounts/{id}/balance?date=` | Залишок грошового рахунку на дату |
| `POST /api/firms/{id}/close-period` | Закриття періоду (`accountant`) |
| `POST /api/auth/ticket` | Обмін тікета з чату на сесію SPA |
