# 2. Архітектура

## Ключовий принцип

Ядро Аури — це звичайний добре описаний API з типізованим SDK і серверними політиками доступу. MCP, MCP Apps, Skills і REST для SPA — тонкі адаптери над одним ядром. Будь-яка помилка LLM чи згенерованого SPA впирається в ті самі перевірки. Найгірше, що може зробити кривий SPA, — показати неправильні цифри. Зламати дані він не зможе.

Так система не залежить від конкретного протоколу: якщо клієнти перейдуть на інший підхід, міняється адаптер, а не система (див. [05-тенденції-mcp-і-альтернативи.md](05-тенденції-mcp-і-альтернативи.md)).

## Як влаштувати MCP-сервер

### 1. Не робити окремий tool на кожен обʼєкт

Обʼєктів близько 700, а моделі погано працюють з набором більше ніж ~30–40 інструментів. Замість цього — кілька загальних інструментів, які описуються метаданими, плюс доменні «макроінструменти»:

| Група | Інструменти |
|---|---|
| Пошук і схема | `describe_entity`, `search` (за довідниками), ресурси `aura://schema/*`, `aura://glossary` (основа — регістр СловарьТерминов) |
| Читання | `get_object`, `query` (типізований DSL фільтрів або read-only SQL тільки по analytics-view з RLS), `run_report(id, params)` |
| Запис | `commit_document` — один виклик; сервер або проводить документ, або відхиляє зі структурованою помилкою |
| Workflow | `my_tasks`, `sign`, `reject(comment)` (коментар обовʼязковий, як в Аурі 3) |
| Доменні макроси | `create_project`, `add_work`, `create_f2_for_work`, `close_month` тощо |

Альтернатива або доповнення — Code Mode: два інструменти `search` і `execute`, агент пише короткий скрипт проти SDK у пісочниці. Перевіряється в прототипі.

### 2. Набір інструментів залежить від ролі

Бухгалтер, еккаунт і ФД бачать різні tools. Модель менше плутається, поверхня атаки менша.

### 3. Запис — один виклик, контроль на сервері

Превʼю проводок перед записом не робимо: ніхто їх не перевірятиме. Сервер або проводить документ, або відхиляє його з поясненням, яке модель може виправити: «Ф3: не заповнено номер рахунку, а його обовʼязково заповнити перед підписом».

Кожен запис несе **ключ ідемпотентності**. Це не для користувача: LLM-клієнти повторюють виклик після таймауту, і без ключа зʼявляться дві однакові Ф2.

Небезпечні операції (видалення, закриття періоду) позначаються `destructiveHint`, щоб клієнт попросив підтвердження.

### 4. Відповіді зручні для LLM

- `structuredContent` разом із коротким текстом, з пагінацією та агрегатами.
- Десятки тисяч рядків у відповідь не віддаються: для них є MCP App або посилання на ресурс.
- Помилки пишуться так, щоб модель могла їх виправити.

### 5. Без стану

Відповідає специфікації 2026-07-28: кожен запит несе токен, контекст користувача відновлюється з нього.

### 6. Аудит

Логуються користувач, клієнт (Claude або ChatGPT), інструмент, параметри та результат. Наступник реєстру змін Аури 3 (регістр ВерсииОбъектов).

## Базові SPA — MCP Apps

Перші кандидати: Консоль проєкту, Консоль підписів, редактор бюджету, імпорт банківської виписки. Відкриваються в чаті й викликають ті самі tools. Модулі з чутливими даними — окремий режим, див. [04-чутливі-дані-і-ризики.md](04-чутливі-дані-і-ризики.md).

Масове введення даних (виписки, бюджети на сотні рядків, табелі) через чат не працює — тут обовʼязково MCP App або SPA.

## Користувацькі SPA

- **Особисті застосунки.** Користувач просить чат-бот згенерувати застосунок. Чат-бот спирається на Skill «aura-app-builder» (шаблон, SDK, правила). Готовий застосунок публікується в App Hub (статичний хостинг із суворим CSP) і ходить у REST з OAuth. За замовчуванням — тільки читання; дозвіл на запис дає адміністратор.
- **Командні застосунки.** Вдалий застосунок реєструється на сервері як `ui://` ресурс і стає доступним усім, хто має відповідні права.

SPA — тонкі клієнти: жодної бізнес-логіки на клієнті, сервер — єдине джерело правди.
