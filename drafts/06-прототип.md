# 6. Прототип (PoC)

## Принцип: Аура 3 — орієнтир, а не специфікація

Рішення з 1С напряму не копіюються. Документація Аури 3 і звіт по конфігурації потрібні, щоб мати уяву про необхідний функціонал: які процеси є в холдингу, які сутності й правила вони зачіпають, що не можна загубити.

Модель даних, процеси й алгоритми Аури 6 проєктуються заново під нову концепцію. Аура 3 використовується так:

- **як чек-лист функціоналу** — щоб нічого суттєвого не пропустити;
- **як джерело тестових даних** — реальні проєкти, Ф2/Ф3, підписи для перевірки сценаріїв;
- **для звірки результатів** — коли нова система рахує те саме (наприклад, AVB чи заборгованість), цифри можна порівняти з Аурою 3.

## Гіпотези

| # | Гіпотеза | Експеримент | Критерій успіху |
|---|---|---|---|
| 1 | Chat-клієнти працюють з Аурою як з системою обліку | Remote MCP-сервер з OAuth; 20–30 сценаріїв («покажи неоплачені Ф3 по проєкту X», «створи Ф2 на роботу Y») в Claude і ChatGPT | ≥ 90% сценаріїв виконано правильно без підказок |
| 2 | Доступ контролюється сервером, а не моделлю | Три користувачі: еккаунт, НЕО, ФД. Еккаунт просить «покажи всі проєкти холдингу» | Сервер віддає тільки дозволене; RLS спрацьовує навіть при помилці в коді tool |
| 3 | Консоль відкривається з чату | Консоль підписів як MCP App (`ui://`) | Відкривається в Claude і ChatGPT, підписує Ф2/Ф3 через tools з `visibility: ["app"]` |
| 4 | Чутливі дані не проходять через провайдера | Зарплатна консоль: `fetch` напряму до Аури через `connectDomains` + одноразовий тікет з `_meta` | Дані не зʼявляються в контексті моделі; в обох клієнтах |
| 5 | Code Mode замінює десятки tools | `search` + `execute` над TS SDK у пісочниці | Ті самі сценарії з п. 1 з точністю не гірше і меншими токенами |
| 6 | Користувач сам генерує SPA | Skill «aura-app-builder»; користувач просить «зроби мені реєстр моїх Ф3 з фільтром по терміну» | Згенерований SPA працює через REST з OAuth без допомоги розробника |

Пункт 4 ставити першим: якщо він провалиться в одному з клієнтів, це змінює архітектуру зарплатного модуля.

## Що потрібно

Поточний стан підготовки — у чек-листі [08-підготовка-до-прототипу.md](08-підготовка-до-прототипу.md).

### Акаунти й доступи

- **Claude**: план із підтримкою власних коннекторів (remote MCP) та MCP Apps. Для командного тесту — Team або Enterprise; почати самому можна на Pro/Max. Назви планів і їх можливості перевірити в поточному прайсі.
- **ChatGPT**: Plus/Pro або Business з увімкненим Developer Mode для MCP-коннекторів; Apps SDK для віджетів.
- **Тестові користувачі**: мінімум три облікові записи в обох клієнтах, по одному на роль.
- **IdP**: Keycloak у Docker (безкоштовно, див. [03-стек-технологій.md](03-стек-технологій.md)) або тестова реєстрація застосунку в Entra ID.

### Інфраструктура

- Публічний HTTPS-ендпоінт: remote MCP викликають сервери Anthropic/OpenAI, а не браузер. На час PoC — Cloudflare Tunnel до локальної машини (безкоштовно) або VPS за $10–20/міс. Домен потрібен справжній: на нього дивляться CSP і OAuth-редиректи.
- PostgreSQL 16+ у Docker.
- Статичний хостинг для SPA (Cloudflare Pages або той самий VPS) на окремому піддомені.
- Машина розробника: Node 22, pnpm, Docker.

### Дані

- **Вивантаження з 1С** по 2–3 організаціях за один рік: проєкти, роботи, Ф2/Ф3/Ф4, контрагенти, співробітники, ролі, підписи, платежі. Формат — JSON, XML або CSV. ПІБ співробітників краще підмінити.
- **Зарплата — синтетична.** Для п. 4 достатньо правдоподібних цифр.
- **BSL-модулі не потрібні**: логіка Аури 6 проєктується заново, а не переноситься з 1С. Вивантаження конфігурації може знадобитися лише точково — щоб зрозуміти, як рахується конкретний показник, якщо документації для цього не вистачає.
- **Набір сценаріїв**: 20–30 фраз, як їх реально скажуть еккаунт, ФМ і бухгалтер, з очікуваним результатом. Без цього PoC не вимірюється.

### Люди і час

- Один розробник TypeScript на повний день, бажано з досвідом PostgreSQL. Досвід MCP не обовʼязковий.
- Носій домену: сценарії, пояснення правил Ф2/Ф3, оцінка результатів. Приблизно 2–3 години на тиждень.

## План на 4 тижні

| Тиждень | Що робимо |
|---|---|
| 1 | Модель даних для зрізу (проєктується заново), імпорт даних, OAuth, перші read-tools у Claude |
| 2 | RLS і ролі, запис Ф2/Ф3, консоль підписів як MCP App, той самий сервер у ChatGPT |
| 3 | Зарплатна консоль з прямим fetch (п. 4), Code Mode (п. 5) |
| 4 | Skill для генерації SPA (п. 6), прогін сценаріїв, звіт за таблицею гіпотез |

## Що можна зробити одразу, без вивантаження з 1С

1. **Модель даних** для зрізу проєкти / роботи / Ф2 / Ф3 / підписи / платежі — нова, під концепцію Аури 6. Звіт по конфігурації використовується як перелік сутностей і реквізитів, щоб нічого не пропустити, і для мапінгу при імпорті даних з 1С.
2. **Каркас монорепо**: `core` (Zod-контракти, доступ), `api` (REST + OpenAPI), `mcp` (адаптер з рольовими tools), `apps/signatures` (MCP App), `skills/aura-glossary` з регістру СловарьТерминов.
3. **Генератор синтетичних даних** на базі схеми, щоб перевіряти п. 1–5 до вивантаження з 1С. Потім синтетика замінюється реальними даними без зміни коду.

## Після PoC

1. **Тіньовий режим, тільки читання.** Дані з 1С переносяться в PostgreSQL, чат-боти відповідають на питання по даних Аури, поки 1С залишається основною системою.
2. **Запис по модулях.** Модулі по черзі переходять на нову систему, 1С по кожному модулю вимикається окремо.
